### Calibration overlay: early-success detection
- Symptom: with the dadinho positioned correctly, the cam reported
  `calMsg = "OK! Edge threshold: 32 (peak: 82). Edges: 144 px, 24×23.
  Limits..."` (success) but the HMI overlay never flipped to the
  green RESULT_OK page. Cam ran cal so fast the 1 Hz pollCam never
  observed `state=1`, so the existing 1→0 edge-transition path didn't
  trigger.
- Fix (bundled into `0185cd3`): mirror the FAILED-prefix detection
  with an `OK!` early-success path. Same gate (msg changed since
  CAL tap + 500 ms min age). On `succeededNow`, flip phase to 1
  (RESULT_OK) instead of 2 (RESULT_FAIL), refresh the cal-snapshot.

### HMI cam-polling stability plan (`5f4935f`)
- Wrote `.plans/hmi-cam-polling-stability.md`. Initial hypothesis:
  the HMI's WebServer lockup was LWIP socket-pool churn between
  inbound `esp_http_server` and outbound `HTTPClient` `pollCam` /
  snapshot fetch / `httpKick`.
- Four levels scoped: A (persistent HTTPClient per cam),
  B (throttle to 0.5 Hz during overlay), C (snapshot via same
  persistent client — defer), D (`-DCONFIG_LWIP_MAX_SOCKETS=16`
  build flag — try in parallel).

### Stability fix attempt 1: Level A + B together (REGRESSED, reverted)
- Implemented Level A: `HTTPClient*` per cam, `setReuse(true)`,
  drop-and-retry on failure.
- 30 s × 1 Hz soak against HMI `/status`: **6/30 (20%) — same as
  baseline.** Some runs slightly worse. Reverted.
- Same soak across all three boards revealed the real shape:
  | Board | Success |
  |---|---|
  | HMI `/status` | 6/30 (20%) |
  | Cam A `/status` | 30/30 (100%) |
  | Cam B `/status` | 30/30 (100%) |
- Same library, same protocol, same WiFi — so the lockup is NOT
  socket-pool churn (cams handle the SAME load fine). It's
  HMI-specific.

### Stability fix attempt 2: Level B alone + diagnostic plan update (`0185cd3`)
- Kept the pollCam throttle (1 Hz → 0.5 Hz while overlay running).
- Reverted Level A back to short-lived `HTTPClient`.
- Updated plan §7b with the comparative soak data + three deferred
  mitigations to investigate next: pin WebServer task to a different
  core, lower LCD pixel clock, throttle background gfx redraws.
- Working hypothesis: RGB-display DMA contention with WiFi on the
  ESP32-S3 — the cams have no LCD, the HMI does.

### Stability fix attempt 3: LCD pixel clock 16 → 8 MHz (`0182851`) — **WORKED**
- Discovered the framebuffer was ALREADY in PSRAM via
  `Arduino_GFX`'s `fb_in_psram=1` panel-config flag, so the "move
  framebuffer to PSRAM" idea was a no-op.
- The contention was on the PSRAM bus: at 16 MHz pclk, the LCD
  peripheral DMAs ~32 MB/s out of PSRAM continuously to refresh the
  800 × 480 × 16 bit panel, starving WiFi's PSRAM access for
  incoming packet buffers.
- Cheapest possible test: halve the pixel clock. One-line change.
- Soak results before/after:
  | Run | HMI | Cam A | Cam B |
  |---|---|---|---|
  | 30 s × 1 Hz baseline (16 MHz) | 6/30 (20%) | n/a | n/a |
  | 30 s × 1 Hz after (8 MHz) | 30/30 (100%) | — | — |
  | 90 s × 1 Hz triple-board (8 MHz) | 80/90 (89%) | 90/90 | 90/90 |
- User confirms no visible flicker on the CrowPanel DIS07050H at
  17 Hz refresh — probably because the panel has some persistence
  and the static-ish placar UI doesn't expose low-refresh flicker
  the way fast video would.
