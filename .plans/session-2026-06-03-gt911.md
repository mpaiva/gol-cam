# Session Plan -- 2026-06-03 (resumed from 2026-05-26)

## Prompt
"add an explicit GT911 init sequence" — after the touch panel on the
CrowPanel HMI stopped registering touches entirely (chip alive on I²C
but config-version reg reads 0xFF and status reg stays 0x00).

## Context (what we knew going in)
- HMI board has been promoted from a passive placar mirror to the
  full-featured placar (cameras push goals to it; on-screen referee
  buttons A+/A-/B+/B- + CAL A / START / RESET / CAL B all map to local
  REST handlers).
- Touch was working at one point (RESET button responded), then went
  totally dead after the debounce thresholds were tightened.
- Symptom diagnosis: chip responds to product-ID query (`"911?"`,
  firmware `0x1060`) but config-version register (`0x8047`) reads
  `0xFF` and status register (`0x814E`) is permanently `0x00`. The
  chip has no factory config burned in, so it refuses to scan.

## Things tried that did NOT work
1. **Soft reset (command 0x02).** No effect — chip stayed in same
   no-scan state.
2. **Factory restore (command 0x05).** *Worse* — this command isn't in
   every GT911 firmware revision, and the unit responded by locking up
   its I²C bus. Every subsequent `requestFrom()` returned `Error -1`
   until power cycle. Code path has been reverted.

## What is on the chip right now (commit `4309e69`)
Inline `gt911` driver in `src_hmi/main.cpp`:

1. Probes product ID + firmware version (diagnostic).
2. Reads config version. If `0xFF` or `< 0x42`, writes a verified
   185-byte 800×480 single-touch config blob lifted from Beken's
   `armino` SDK (`middleware/driver/tp/tp_gt911.c`, the `#else`
   branch). Then writes `1` to `0x8100` to commit.
3. Puts command register in normal scan mode (`0`).
4. Clears status byte so the first touch produces a fresh "ready"
   event.
5. Polling loop reads status every ~loop iteration; on bit 7 set,
   reads 7-byte point 1 record and decodes X/Y.

The chunked-write helper (`writeRegs`) splits the 185-byte payload
into 16-byte transactions because Wire's default 128-byte buffer
can't hold the whole thing in one go.

## What to verify next session
1. **Did the config write take?** Plug in HMI, watch serial monitor
   (`pio device monitor -e crowpanel_hmi`). Expect:
   ```
   [gt911] product_id = "911?"
   [gt911] firmware = 0x1060
   [gt911] config version = 0xFF
   [gt911] no valid config — writing fallback blob
   [gt911] writing 800x480 config blob (Beken/armino, ver 0x42)
   [gt911] post-write config version = 0x42 (want 0x42)
   [gt911] init complete, polling enabled
   ```
   If `post-write config version` reads `0x42`, the chip accepted the
   config and should now scan. Touch any button — `[gt911] status=...`
   diagnostic prints every 500 polls should show non-zero values, and
   button-press handlers should fire.

2. **If I²C is still locked up from cmd 0x05:** unplug for >5 seconds
   to fully drain the panel's 3V3 rail, then replug. GT911 will reset
   to its default state.

3. **If config writes but touches still don't fire:** the
   drive/sense thresholds in the Beken blob were tuned for *their*
   800×480 panel, not the Elecrow DIS07050H. Touches may register but
   only at very high pressure, or the chip may keep reporting `status
   = 0x00` because the sensing threshold is too high. Path forward
   then is to capture the chip's behaviour via Goodix's Windows
   tuning tool, or try alternative config blobs (LovyanGFX / TouchGFX
   demos have a few).

## Update: config-write attempt confirmed FAILED at chip level (later in session)

After flashing the config-blob writer, the user said "buttons aren't
working". Pyserial-based serial capture revealed:

```
[gt911] product_id = "911?"
[gt911] firmware = 0x1060
[gt911] boot config version = 0xFF
[gt911] no valid config — writing fallback blob
[gt911] writing 800x480 config blob (Beken/armino, ver 0x42)
[gt911] post-write pre-commit readback: 42 20 03 E0 01 01 3D 00
[gt911] post-commit config version = 0xFF (want 0x42)   ← REVERTED
[gt911] init complete, polling enabled
[gt911] status=0x00 (poll #500)
[gt911] status=0x00 (poll #1000)
...
```

What we learned:
- **Writes succeed** — chip accepts and stores our 185 bytes in config
  RAM. Pre-commit readback shows `42 20 03 E0 01 01 3D 00` (the
  first 8 bytes of the Beken blob) exactly. Bus is healthy.
- **Commit silently fails** — `0x8100 ← 1` (and `0x8101 ← 1`) does NOT
  apply the config; version reverts to `0xFF`. Tried dual-commit, 50ms
  + 500ms delays, recomputed-from-source checksum (verified `0x4F`
  correct via Python). Same result every time.
- **Status reg stays `0x00` for thousands of polls** — chip is alive
  and answering I²C but is NOT in scan mode.

This is a chip-level rejection, not a firmware bug. The most plausible
explanation is that the GT911 NVRAM on this unit is in a "factory blank
+ commit-locked" state — possibly because the unit shipped with the
factory programming step skipped. Software workarounds (config-blob
writes, soft reset, factory-restore command) have all failed; one
(`cmd 0x05`) bricked the I²C bus until power cycle.

## RESOLUTION — 2026-06-03 (later that day)

Touch is now fully working. All 8 buttons (A+/A-/B+/B-, CAL A,
START, RESET, CAL B) fire correctly. The full saga in summary:

1. **The GT911's commit machinery IS broken** — config version still
   reads `0xFF` after `0x8100` + `0x8101` writes; the chip refuses
   our blob and reverts. That part of the diagnosis was correct.
2. **The wide RST-pin sweep clobbered the RGB display** — almost
   every general-purpose GPIO on this board is wired to LCD data /
   sync lines; pinMode-as-OUTPUT on those redirects them off the
   LCD peripheral. Symptom: stuck white screen. Fix: rip out the
   sweep, power-cycle. Lesson: confirm "general-purpose" means
   general-purpose on a given board before pulsing pins.
3. **The chip is actually scanning anyway.** After the panel
   recovery, `/debug/touch` showed `touch_count: 140` with valid
   `(last_x, last_y)` even though the config version still said
   `0xFF`. The chip has SOME mode where it scans and reports
   touches via the status register even without a host-loaded
   config — possibly a hardcoded factory-default. The commit
   appears to be cosmetic; scanning runs regardless.
4. **The real bug was in OUR firmware** — the release-fire scheme
   in `serviceTouch()` required `held >= MIN_PRESS_MS (30ms)`. The
   chip reports touches as one-shot status-bit blips (not a held
   "data ready" window), so `gt911::touched` flips back to false
   between polls during a real press, the apparent "release" event
   has `held < 30ms`, and the action is silently dropped. Visual
   feedback fired (color change) but the action queue did not.
5. **Fix**: fire on press with a 250 ms cooldown. Implemented in
   commit `8f53704`. Verified: 3 taps on A+ → score = 3; all 8
   buttons confirmed working.

  `flush` in handlers, or trimming `String` use in JSON builders.
