  drawButton(prev/btn) in `serviceTouch()`. Title bumped to text

  dimensions, dismiss path sets `dirtyHeader` too since the header
  is now also under the overlay.

- **`dcb85b7`** — dismiss path now calls `renderFull()` directly

  `dirtyButtons` handler is hard-coded to repaint only button index
  5 (START, the only one whose label changes via pollCam), so

### Option C: cam-snapshot preview in the overlay (SHIPPED, commit `ae41369`)
Pulls the cam's `/cal-snapshot` JPEG into a PSRAM buffer, decodes
with TJpg_Decoder, renders into a 320×240 region of the calibration
overlay. Operator can now see what the cam was looking at and
diagnose failures ("dark image, no edges found → cam needs more
light") at a glance.

Tech notes:
- Added `bodmer/TJpg_Decoder@^1.1.0` to platformio.ini for crowpanel_hmi
  env.
- 32 KB PSRAM buffer alloc'd once at boot via `ps_malloc`; observed
  JPEG sizes are ~2 KB but the cam can grow larger for textured
  scenes.
- TJpgDec callback receives ABSOLUTE screen coords (already offset
  by what was passed to `drawJpg(SNAP_X, SNAP_Y)`), so the callback
  passes `x, y` straight to `gfx->draw16bitRGBBitmap` without
  further adjustment. The first version of the callback was
  double-adding `SNAP_X + x`, putting pixels off-screen.
- Two-fetch trigger: once on overlay raise (instant preview of
  previous attempt's frame), once on state-transition to RESULT
  (refresh to THIS attempt's frame). Result phase auto-dismiss
  extended from 3 s to 6 s so the second fetch has time to
  complete and the user actually sees the new frame.
- Anti-flicker: `snapVersion` counter bumps on each successful
  fetch; `drawCalOverlay` only re-decodes the JPEG when the
  version changes since last paint. Without this gate, every
  `dirtyOverlay` tick (caused by polling, state changes, etc.)
  was re-fillRect-ing and re-decoding the snap area.
- The full-screen white background fill that opens
  `drawCalOverlay` is now done in four strips AROUND the snap
  area instead of one rect through it. Otherwise the version
  gate would refuse to re-decode, leaving the snap area white
  between fetches.

Bug journey along the way:
| # | Symptom | Root cause | Fix |
|---|---|---|---|
| 1 | Snapshot fetch never logged | User wasn't tapping CAL during my serial-capture windows; bash `echo` prompts are invisible to the user | Use AskUserQuestion to coordinate tap timing; capture in background and read the saved log after |
| 2 | `TJpgDec.drawJpg returned 1` but no image visible | Callback was double-adding SNAP_X/Y → pixels at (560+, 300+), off-screen | Pass `x, y` straight from the callback to gfx without offset |
| 3 | Image renders for first fetch, "(carregando…)" persists for second | State-transition request sets `calSnapReady=false`, drawCalOverlay paints placeholder over the image, second fetch never re-paints because result phase auto-dismissed before fetch completed | Extend result-phase timeout from 3 s to 6 s |
| 4 | Image renders but flickers heavily | Every `dirtyOverlay` tick re-fillRect'd + re-decoded the snap area, even when the JPEG hadn't changed | Add `snapVersion` counter + version-gated decode in drawCalOverlay |
| 5 | Less flicker but still some | Top-of-`drawCalOverlay` fillRect was clearing the snap area on every call; version-gate then refused to re-decode | Replace the fullscreen fillRect with 4 strips that leave the snap area untouched |
